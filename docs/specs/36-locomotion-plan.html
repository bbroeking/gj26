Spec 36 · Godot 4 · Player Locomotion

From capsule to fluid character

An 11-step path to walk, run, roll, dash, and jump that feel right.

Target feel — definition of done

A player drops into the crypt, holds W, kites a 3-pack, rolls through a sweep, dashes to cover, jumps a gap. They should feel: no foot-slide, no animation snap, no input loss, no missed jumps, no skiddy stops. That's the bar.

Where we are right now

  • Player.tscn is a capsule CharacterBody3D. No rigged mesh attached.
  • Movement: SPEED=5.0, ACCEL=10, GRAVITY=22 — single-value linear lerp toward target velocity. No accel/decel split, no rotation, no states.
  • Camera: damped follow + orbit + zoom done (spec 09). Camera-relative input projection wired.
  • Animations available: Meshy-rigged enemy/boss GLBs ship with Idle + Walk + Run. Roll / Dash / Jump clips do not yet exist for any character.
  • AnimationTree has never been used in this project. New territory.

The architecture

Don't put a single BlendSpace1D at the root and call it done. The right shape nests three things: a OneShot for action-overlays (attacks, hit-reacts) wrapping a StateMachine of locomotion + committed-action states, with the locomotion state itself containing a BlendTree with the walk↔run gradient. This is the load-bearing decision — it gives us a slot for spec 37 (attacks) without a rewrite.

AnimationTree (root: StateMachine)
└─ Output
   └─ OneShot ("ActionOverlay")     ← attacks, hit-react, cast
      ├─ in:    StateMachine ("Base")
      │         ├─ Idle  ──┐
      │         ├─ Locomotion ──┤   ← BlendTree
      │         │              └─ BlendSpace1D
      │         │                    Idle (0.0)
      │         │                    Walk (0.4)
      │         │                    Run  (1.0)
      │         ├─ Roll   (At End → Locomotion)
      │         ├─ Dash   (At End → Locomotion)
      │         ├─ JumpStart → JumpAir → JumpLand → Locomotion
      │         │
      │         └─ (TimeScale node feeds the BlendSpace
      │            output, scaled 0.7×–1.3× by velocity)
      └─ shot:  Animation ("Attack01" / swapped at runtime)

Why OneShot first. Without it, every overlay attack we add later has to fight the state machine for the Output slot. OneShot says "play this for N frames, then get out of the way" — exactly the contract attacks need.

Why StateMachine inside. Roll, Dash, and the three Jump phases are discrete — they don't blend. The state machine handles their committed-with-recovery shape natively.

Why a BlendTree inside the Locomotion state. Walk↔run does blend, continuously, driven by velocity. Different node type for a different job.

4

Drive the blend from velocity each frame

In player_controller.gd, lerp the blend parameter from velocity.length() / MAX_SPEED. Lerp factor 12 — high enough to feel responsive, low enough that input release doesn't pop.

const MAX_SPEED   := 6.0
const BLEND_LERP  := 12.0
var _blend := 0.0

func _update_locomotion_blend(delta: float) -> void:
    var target := clamp(velocity.length() / MAX_SPEED, 0.0, 1.0)
    _blend = lerpf(_blend, target, BLEND_LERP * delta)
    anim_tree.set("parameters/Base/Locomotion/BlendSpace1D/blend_position", _blend)
Feels-good
WASD → smooth idle → walk → run gradient with no snap on press or release.
5

Eliminate foot-slide with an AnimationNodeTimeScale

The blend alone doesn't fix slide — Walk plays at fixed cadence regardless of real speed. Insert a TimeScale node downstream of the BlendSpace, scale it by velocity.length() / WALK_REF_SPEED, clamp to 0.7×–1.3× so the cycle doesn't go cartoonish at sprint.

Numbers
Calibrate WALK_REF_SPEED by eye in the editor. Usually within 10% of the value Meshy authored.
Why not root motion
Meshy rigs often have non-1.0 scale → root motion returns garbage. Pitfall #4.
Feels-good
no foot-slide at any speed, sprint included.
6

Yaw the mesh toward movement direction

Currently the body moves but doesn't turn — only the camera does. Rotate the mesh (not the CharacterBody) toward velocity via lerp_angle. Gate on a minimum speed so idle doesn't drift.

const ROT_SPEED := 10.0

if velocity.length() > 0.5:
    var target_yaw = atan2(velocity.x, velocity.z)
    mesh.rotation.y = lerp_angle(mesh.rotation.y, target_yaw, ROT_SPEED * delta)
Feels-good
holding W → tapping A makes the character arc into the turn, not strafe.
7

Split ACCEL / DECEL / TURN_DECEL

Current single ACCEL=10 handles speeding up and slowing down identically. Split into three so stops feel deliberate and direction-reversals feel snappy.

Numbers
ACCEL=20 (start), DECEL=18 (stop), TURN_DECEL=30 (reverse). Sprint via RUN_SPEED=6.0 on Shift, WALK_SPEED=3.0 baseline.
Feels-good
stopping mid-run feels deliberate, not skiddy. Reversing W→S is instant, not delayed.

10

Jump — impulse + coyote + buffer

Three states stacked: JumpStart → JumpAir → JumpLand. Vertical impulse on press, gravity takes over, landing recovery on floor-contact. Coyote and buffer windows are non-negotiable — without them, jumps feel "missed" even with correct input.

Feels-good

11

Playtest pass — record, watch, tune

20-minute play session. Record the screen. Watch back at 0.5×. Mark every moment where movement reads "off." For each: identify the tunable (ACCEL, ROT_SPEED, WALK_REF_SPEED, roll duration, dash burst, jump gravity), adjust, replay. Two or three iteration loops is normal.

Pitfalls to remember

Every one of these has bitten Godot 4 devs in the issue tracker. Save yourself the hour.

1. travel() vs advance_condition
Conditions only auto-fire direct-neighbour transitions. Use conditions for ambient locomotion, travel() for event triggers (roll, dash, jump).
2. travel() silently fails with no valid path
If a transition isn't drawn in the editor, travel() returns without error. Sanity-check each state by triggering it from _ready during dev.
3. Non-looping animations don't restart on re-travel
After Roll finishes, travel("Roll") is a no-op. Use state_machine.start("Roll") to force-restart.
4. Scaled rig breaks root motion
Non-(1,1,1) scale on the Skeleton3D or its parent → get_root_motion_position() returns garbage. Set model scale to 1.0 in the Import dock, or bake in Blender.
5. OneShot interruption-after-completion bug
Stacking OneShot fires can cause the first to revive after the second ends. Use a single OneShot whose embedded animation you swap at runtime, fired via ONE_SHOT_REQUEST_FIRE.
6. AnimationLibrary cloning shares tracks silently
Two scenes using the same AnimationLibrary share edits. Set Local-to-Scene on the AnimationTree, or duplicate per-character.
7. floor_snap_length eats jumps
A non-zero snap will yank the character back to the floor on small jump impulses. Set floor_snap_length = 0 while velocity.y > 0.
8. velocity = direction * speed * delta
move_and_slide() already integrates over delta. Multiplying yourself produces a controller that runs at delta² — unusably slow. Common typo from move_and_collide muscle memory.

What this is not

Scope guard

This is the locomotion arc only. Attack animations, ability casts, hit-reacts, status-tick visuals, climbing, swimming, mounts, and emotes are explicitly out of scope. The architecture (OneShot channel) leaves room for attacks in spec 37, but no attack work happens here.
